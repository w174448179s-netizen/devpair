# 智谱 GLM JSON 输出带 markdown 代码块包裹

## 现象

智谱 GLM 系列模型（glm-4、glm-4.5-air 等）在要求输出 JSON 时，经常用 markdown 代码块包裹：

````
```json
{
  "persons": ["张三"],
  "locations": ["北京"]
}
```
````

直接用 Jackson/Gson 解析会报 `JsonParseException`，因为字符串以 ` ```json ` 开头，不是合法 JSON。

## 影响

- JSON 解析失败 → 业务流程中断
- 如果解析失败后直接吞错返回 null，上层逻辑拿到空结果，问题更难排查

## 原因

智谱 GLM 的训练数据中大量包含 markdown 格式的代码块，模型倾向于用 markdown 包裹所有"代码"格式的内容，包括 JSON。这不是 bug，是模型行为。

DeepSeek 偶尔也有类似行为，但频率低。Ollama 本地模型通常干净。

## 解决方案

**解析前预清理，不作为错误处理，是标准流程。**

```java
// 去除 markdown 代码块标记
String cleaned = raw.replaceAll("(?s)^\\s*```(?:json|JSON)?\\s*\\n?", "")
                    .replaceAll("(?s)\\n?\\s*```\\s*$", "")
                    .trim();
```

完整方案见 `~/devpair/rules/components/llm-output.md`，预清理工具类 `LlmOutputCleaner` 统一收敛所有模型的输出清理逻辑。

## 教训

1. **LLM 输出不可信，解析前必须预清理**——这不是异常处理，是标准流程
2. **不同模型行为不同**，清理逻辑要覆盖所有在用模型
3. **rawResponse 必须存日志**，解析失败时能快速定位是模型输出问题还是代码问题
4. **清理逻辑统一收敛**，不要在每个调用点散落重复代码

# 文档内容中的引号导致 JSON 解析失败

## 现象

源文档内容中包含 `"`（如对话、引述、标注等），LLM 读取文档内容后输出 JSON，文档中的引号未转义直接放入 JSON 字符串值中，导致 JSON 解析报错。

```
源文档内容：他说"这个方案不行"，然后走了。

LLM 输出（错误）：
{"summary": "他说"这个方案不行"，然后走了。"}

→ Jackson/Gson 解析报错：Unexpected character ('这' (code 27408))
```

## 影响

- 解析失败 → 业务流程中断
- 间歇性出现——只有文档内容恰好含 `"` 时触发，难以稳定复现
- rawResponse 看起来"像 JSON"，排查时容易忽略是引号未转义

## 原因

LLM 在生成 JSON 时，对于用户传入的文档内容中的 `"`，不一定会自动转义为 `\"`。尤其是：
- 智谱 GLM：中文引号场景下转义不稳定，偶发不转义
- DeepSeek：英文引号场景偶发不转义
- 文档内容越长、引号越多，出错概率越高

这是 LLM 的固有局限——它不是 JSON 序列化器，对字符串转义的可靠性不如程序化序列化。

## 解决方案

**三层防御，但每层都有局限，必须配合使用：**

### 第 1 层：输入侧预处理（降低概率）

传给 LLM 之前，对文档内容中的 `"` 替换为中文引号：

```java
String safeInput = rawDocument.replace("\"", "「").replace("\"", "」");
```

**局限：LLM 可能在处理过程中将 `「」` 又转回 `"`**，输入侧替换不是万能的，只是降低出错概率。

### 第 2 层：Prompt 显式约束

在 prompt 中明确要求：

```text
1. 输出 JSON 时，字符串值中的双引号必须转义为 \"，反斜杠转义为 \\。
2. 不要修改内容中的引号格式，保持原样输出。
```

不能只靠这一层——LLM 不一定遵守。

### 第 3 层：输出侧修复兜底（必须实现）

解析失败时，逐字符扫描 JSON，区分结构引号和内容引号，对内容引号补 `\` 转义。实现见 `rules/components/llm-output.md` 第四章 `escapeInnerQuotes` 方法。

**三层缺一不可**：第 1 层降低概率，第 2 层引导 LLM 行为，第 3 层兜底保底。

### 架构层面：避免在 JSON 中放原始文档内容

最根本的解决方案是**设计输出 schema 时避免自由文本字段**：

- 用枚举代替文本（`"status": "REJECTED"` 而非 `"reason": "他说"不行""`）
- 用布尔/数字代替描述（`"score": 85` 而非 `"evaluation": "很好，85分"`)
- 如果必须输出文本，限制长度并要求 LLM 概括而非原文搬运

## 教训

1. **LLM 不是 JSON 序列化器**——不能假设它会正确转义特殊字符
2. **输入侧替换会被 LLM 绕过**——`「」` 可能被转回 `"`，不能只靠输入侧
3. **输出侧修复必须实现**——这是最后防线，`escapeInnerQuotes` 逐字符扫描兜底
4. **最好的方案是不放原文**——设计 schema 时用结构化字段代替自由文本
5. **间歇性 bug 最危险**——只有特定内容才触发，测试时容易漏
6. **rawResponse 存日志是底线**——解析失败时能看到原始输出，快速定位
