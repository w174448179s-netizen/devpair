# 任务拆分规范

基于架构方案，在 `./tasks/` 目录生成整套开发文档。

---

## 一、拆分原则

### 1. 粒度标准

一个 task = **一个可独立交付的功能单元**。标准：

- 有明确的输入和输出
- 完成后可以独立验证（能跑、能测）
- 不依赖其他 task 的代码细节（只依赖接口约定）
- 一个 task 的开发工作量控制在 30-60 分钟内

### 2. 什么该拆成独立 task

| 类型 | 示例 |
|------|------|
| 项目初始化（基础架构） | 项目骨架、统一响应格式、全局异常处理 |
| 数据库建表 + 枚举 | DDL、状态/类型枚举类 |
| 一个完整的数据模型 + CRUD | 文档上传、解析、存储 |
| 一个独立的算法/服务 | Tika 解析服务、PgVector 检索服务 |
| 一个对外接口 | RAG 问答 API、文件上传 API |
| 编排/调度模块 | Pipeline 编排器、定时调度、线程池配置 |
| 集成与验证 | 端到端测试、跨模块一致性检查 |

### 3. 什么不该拆

- 不把"写一个 DTO"拆成独立 task——它是 CRUD task 的交付物
- 不把"配置 application.yml"拆成独立 task——它属于项目初始化
- 不把"代码 review"拆成独立 task——它在每个 task 的验收标准里
- 不把单元测试拆成独立 task——它是每个 task 的交付物

### 4. 任务顺序

- 项目初始化（骨架 + 规范就位）→ 第一个 task
- 数据库建表 + 枚举 → 第二个 task
- 被依赖的模块 → 在前（如 Entity/Mapper 在 Service 之前）
- 编排/调度模块 → 最后（依赖所有业务模块）
- 集成验证 → 最后一个 task

## 二、执行步骤

1. 读取 `~/devpair/AGENTS.md`，了解技术偏好和核心约束
2. 基于架构方案，按上述拆分原则拆解任务
3. 在 `./tasks/` 下生成：
   - `{项目名}开发任务总览.md` — 任务索引 + 执行规则 + 设计决策 + 流转链
   - `任务0-xxx.md`、`任务1-xxx.md`... — 每个子任务一个独立文件

---

## 三、总览文件格式

`{项目名}开发任务总览.md` 是整个项目的任务入口和规则中心。不包含任何任务的具体内容，只做索引和执行规则说明。

```markdown
# {项目名} — 开发任务总览

## 整体架构简述
{2-3 句话描述项目是什么、技术栈、核心模块}

## 文档路径约定
项目根目录：{绝对路径}

架构子文档（按需读取）：

| 文档 | 路径 | 引用任务 |
|------|------|---------|
| {架构设计文档} | {路径} | 任务 0、2、... |
| {数据库设计} | {路径} | 任务 1、2、... |

任务文件（执行哪个任务读哪个文件）：

| 任务 | 文件路径 |
|------|---------|
| 任务 0 | {路径}/tasks/任务0-项目初始化.md |
| 任务 1 | {路径}/tasks/任务1-数据库建表与枚举.md |
| ... | ... |

## 执行模式
1. 读取 `~/devpair/AGENTS.md`，了解技术偏好和核心约束
2. 读取本文件，了解执行顺序和设计决策
3. 按编号 0 → 1 → ... → N 顺序执行
4. **执行任何任务前，必须先读取 `~/devpair/rules/` 下该任务标注的规则文件**
5. **每个任务完成后，必须停止并汇报**：生成了哪些文件、测试结果
6. **等待回复"继续"后，再读下一个任务文件**
7. 任务内子步骤可连续执行
8. 遇到失败：报告原因，停止执行

## 任务执行顺序
0（骨架）→ 任务0-项目初始化.md
 ↓
1（DDL + 枚举）→ 任务1-数据库建表与枚举.md
 ↓
2（{入口模块}）→ 任务2-{入口模块}.md
 ↓
...
 ↓
N（{编排模块}）→ 任务N-{编排模块}.md

## 设计决策速查
> 架构方案中的关键决策，必须在总览中显式声明，避免任务执行时遗漏。

| 决策 | 选项 | 当前选择 |
|------|------|---------|
| 包名规范 | — | com.{org}.{project} |
| 调度/工作线程 | 共用 / 分离 | {选择} |
| 状态转换 | Java 判断 / 原子 SQL | {选择} |
| 重试策略 | 创建新记录 / 原地重置 | {选择} |
| LLM 评分阈值 | 自动通过 / 待审核 | {选择} |
| System Prompt | 硬编码 / 外部文件 | 外部文件 |
| {其他决策} | — | {选择} |

## 数据流转链（有 Pipeline/工作流时必写，无则删除本节）
> 标注每个阶段的输入输出、状态分支、重试机制。

{入口模块}
    ↓ 创建数据记录 + 创建 PipelineTask({阶段1})
    ↓
{TaskHandler1}
    ↓ 处理 → 创建 PipelineTask({阶段2})
    ↓
{TaskHandler2}
    ↓ 处理 → 创建 PipelineTask({阶段3})
    ↓
...
    ↓
{最终TaskHandler} → 写入目标存储 → 完成

## 通用约束
1. 所有子任务文档只定义项目目标和交付物，通用约束通过「需加载的规则文件」列表引用
2. 代码与通用规则冲突时，以 `~/devpair/rules/` 内规范为准
3. 项目特殊定制在对应 task 文档的「额外说明」中写明
4. 开发完成后区分知识：
   - 项目独有方案：留存 tasks 目录
   - 通用组件经验、踩坑记录：归档至 `~/devpair/notes/pitfalls/`
```

## 四、任务文件格式

每个任务文件必须严格使用以下结构：

```markdown
# 任务 N：{任务标题}

## 已有代码
{前序任务产出的 Entity/Mapper/Service/枚举，让执行方知道什么已经存在，可以直接引用}
如：DocumentEntity、DocumentMapper、DocumentStatus 枚举（任务 1 产出）

## 前置依赖
无 / 任务 N（必须完成后才能启动本任务）

## 需加载的规则文件（执行前必须逐一读取）
- ~/devpair/rules/core/always-apply.md
- ~/devpair/rules/java/coding-rules.md
- {其他与本任务相关的规则文件，精确列出，不要多也不要少}

## 参考文档（架构设计细节，执行前读取）
{列出本 task 直接相关的架构文档路径及章节。内容可能包括：接口定义、数据库表结构、数据流图、业务规则等。如果任务目标已足够清晰，删除本节}

## 实现步骤

### 步骤 N.1：{子步骤标题}
{具体描述要实现什么。复杂逻辑必须展开写清楚：}
- 算法/处理流程：分点描述
- 异常处理策略：什么情况走什么路径
- 边界条件：空数据、超时、超限等
- 关键 SQL：如有原子操作，写出核心 SQL 语句
- LLM 调用：如有，写明 prompt 加载方式、输出预清理、解析失败处理

### 步骤 N.2：{子步骤标题}
{同上，每个步骤独立编号}

### 步骤 N.3：验证
{本任务的验证方式：编译通过、测试通过、端到端验证等}

## 交付物清单
1. {具体的文件路径/类名，如：src/main/java/.../DocumentController.java}
2. {单元测试类名}

## 验收标准
1. 功能满足所有实现步骤描述
2. 代码严格遵守【需加载的规则文件】内全部约束
3. 处理边界异常：超时、空数据、超限文件等
4. 代码注释完整，符合编码规范
5. 单元测试覆盖核心逻辑（正常路径 + 异常路径）

## 额外说明
{本项目独有的特殊调整、临时兼容方案。如果没有，删除本节}
```

## 五、任务类型参考

不同类型的任务，实现步骤的写法不同。以下是常见类型的参考：

### 1. 项目初始化（任务 0）

步骤覆盖：pom.xml 依赖、包结构（只建有实际文件的包）、application.yml 配置、全局异常处理、统一响应格式。

验证：`mvn clean compile` 通过，`mvn spring-boot:run` 启动成功。

### 2. 数据库建表 + 枚举（任务 1）

步骤覆盖：DDL（IF NOT EXISTS、BIGSERIAL 主键、关键字段索引）、枚举类（每个值有 Javadoc、状态/类型类枚举名以 Status/Type/Stage 结尾）。

验证：schema.sql 在 PostgreSQL 中执行成功；枚举编译通过。

### 3. Entity + Mapper + Service（任务 2+）

步骤覆盖：Entity（@Data @Builder、字段 Javadoc、状态字段用枚举）、Mapper + XML（原子认领 SQL 如有、重置 SQL 如有）、Service 接口 + 实现。

已有代码需列出：DDL 表名、枚举类名。

验证：@MybatisTest，insert + selectById 能读回，枚举映射正确。

### 4. 核心业务模块（含 LLM 调用）

步骤覆盖：DTO 定义、配置类（LLM 配置、Prompt 加载）、Service 核心逻辑。

LLM 调用注意事项必须写明：
- System Prompt 从文件加载，禁止硬编码
- LLM 输出预清理（如 Markdown 包裹，在解析前去除）
- rawResponse 完整存入日志
- 解析失败处理路径

已有代码需列出：依赖的 Entity/Mapper/Service/枚举。

### 5. 编排/调度模块

步骤覆盖：线程池配置（调度池 + 工作池分离）、TaskHandler 接口 + 策略模式、Orchestrator 核心逻辑。

关键原则必须写明：
- 认领与执行分离：Orchestrator 只管认领 + 分发，TaskHandler 只管业务逻辑
- 状态转换走原子 SQL
- 重试 = 原地重置原 task 状态为 WAITING，不创建新记录

已有代码需列出：全部 Entity/Mapper/Service/枚举。

验证：端到端测试全链路 + 并发认领测试（两线程认领同一任务）。

### 6. 前端管理台（独立项目）

步骤覆盖：项目初始化、API 封装、路由、页面逐个开发。

独立目录、独立构建，与后端主项目分离。

## 六、重要约束

- task 文档**只描述项目目标和交付物**，禁止大段复制通用约束
- 通用约束统一通过「需加载的规则文件」列表引用，让 AI 执行 task 时自行读取
- 架构方案中的设计细节（接口定义、数据库表结构、数据流等）放入「参考文档」，不要复制到实现步骤中
- 「参考文档」只列对本 task 有直接参考价值的文档，模糊的全局文档不列
- **复杂逻辑必须展开到步骤级别**：算法流程、异常处理策略、原子 SQL、LLM 调用模式等，不能一句话概括
- **「已有代码」必须列出前序任务的关键产出**：Entity/Mapper/Service/枚举类名，让执行方知道可以直接引用什么
- 如果任务涉及通用组件（LangChain4j、PgVector、文件上传等），必须在「需加载的规则文件」中列出对应规则文件
- 「需加载的规则文件」列表要精确——只列本 task 真正需要的，不多列也不少列
- 交付物清单要具体到文件路径，不要写"相关代码"这种模糊描述
