# 任务拆分规范

基于架构方案，在 `./tasks/` 目录生成整套开发文档。

---

## 一、拆分原则

### 1. 粒度标准

一个 task = **一个可独立交付的功能单元**。标准：

- 有明确的输入和输出
- 完成后可以独立验证（能跑、能测）
- 不依赖其他 task 的代码细节（只依赖接口约定）
- 一个 task 的开发工作量控制在 30-60 分钟内

### 2. 什么该拆成独立 task

| 类型 | 示例 |
|------|------|
| 项目初始化（基础架构） | 项目骨架、统一响应格式、全局异常处理 |
| 一个完整的数据模型 + CRUD | 文档上传、解析、存储 |
| 一个独立的算法/服务 | Tika 解析服务、PgVector 检索服务 |
| 一个对外接口 | RAG 问答 API、文件上传 API |
| 集成与验证 | 端到端测试、跨模块一致性检查 |

### 3. 什么不该拆

- 不把"写一个 DTO"拆成独立 task——它是 CRUD task 的交付物
- 不把"配置 application.yml"拆成独立 task——它属于项目初始化
- 不把"代码 review"拆成独立 task——它在每个 task 的验收标准里
- 不把单元测试拆成独立 task——它是每个 task 的交付物

### 4. 任务顺序

- 基础架构（数据库、统一响应、异常处理）→ 第一个 task
- 数据模型 → 在业务 task 之前
- 被依赖的模块 → 在前
- 集成验证 → 最后一个 task

---

## 二、执行步骤

1. 读取 `~/devpair/AGENTS.md`，了解我的技术偏好和核心约束
2. 基于我们讨论的架构方案，按上述拆分原则拆解任务
3. 在 `./tasks/` 下生成：
   - `overview.md` — 整体架构简述、任务顺序、模块依赖、全局约定
   - `task-01-xxx.md`、`task-02-xxx.md`... — 每个子任务一个独立文件

---

## 三、overview.md 格式

```markdown
# {项目名称} — 开发总览

## 整体架构简述
{2-3 句话描述项目是什么、技术栈、核心模块}

## 任务执行顺序（严格按顺序推进）
1. Task01：{任务名称} — {一句话说明}
2. Task02：{任务名称} — {一句话说明}
...

## 模块依赖关系
Task01（基础架构）
  ↓
Task02（{模块名}） ← 依赖 Task01
  ↓
Task03（{模块名}） ← 依赖 Task01、Task02
...

## 全局约定
1. 所有子任务文档只定义项目目标，通用约束通过「需加载的规则文件」列表引用
2. 代码与通用规则冲突时，以 ~/devpair/rules/ 内规范为准
3. 项目特殊定制在对应 task 文档的「额外说明」中写明
4. 开发完成后区分知识：
   - 项目独有方案：留存 tasks 目录
   - 通用组件经验、踩坑记录：归档至 ~/devpair/notes/pitfalls/
```

## 四、task 文档格式

每个 task 文档必须严格使用以下结构：

```markdown
# Task XX：{任务名称}

## 所属模块
{模块名称}

## 前置依赖
无 / Task XX（必须完成后才能启动本任务）

## 任务目标
{清晰描述要实现什么。只写项目专属需求，不粘贴通用约束。}

## 需加载的规则文件（执行前必须逐一读取）
- ~/devpair/rules/core/always-apply.md
- ~/devpair/rules/java/coding-rules.md
- {其他与本任务相关的规则文件，精确列出，不要多也不要少}

## 参考文档（架构设计细节，执行前读取）
{列出本 task 直接相关的架构文档路径。内容可能包括：接口定义、数据库表结构、数据流图、业务规则等。如果任务目标已足够清晰，删除本节}

## 交付物清单
1. {具体的文件路径/类名，如：src/main/java/.../DocumentController.java}
2. {单元测试类名}

## 验收标准
1. 功能满足任务目标描述
2. 代码严格遵守【需加载的规则文件】内全部约束
3. 处理边界异常：超时、空数据、超限文件等
4. 代码注释完整，符合编码规范
5. 单元测试覆盖核心逻辑（正常路径 + 异常路径）

## 额外说明
{本项目独有的特殊调整、临时兼容方案。如果没有，删除本节}
```

---

## 五、重要约束

- task 文档**只描述项目目标和交付物**，禁止大段复制通用约束
- 通用约束统一通过「需加载的规则文件」列表引用，让 AI 执行 task 时自行读取
- 架构方案中的设计细节（接口定义、数据库表结构、数据流等）放入「参考文档」，不要复制到任务目标中
- 「参考文档」只列对本 task 有直接参考价值的文档，模糊的全局文档不列
- 如果任务涉及通用组件（Tika、PgVector、文件上传等），必须在「需加载的规则文件」中列出对应规则文件
- 「需加载的规则文件」列表要精确——只列本 task 真正需要的，不多列也不少列
- 交付物清单要具体到文件路径，不要写"相关代码"这种模糊描述
